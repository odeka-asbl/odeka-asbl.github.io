# ODEKA A.S.B.L. website — working notes for Claude Code

This file is read automatically at the start of every Claude Code session opened
in this repo, on any machine. Its job is to hold the *tacit* knowledge — debugging
traps, reasoning behind non-obvious choices, exact gotchas — that isn't visible
just from reading the code once. The **procedural** how-to guide (add a person,
add a project, toggle News, post a job, set up a new computer) lives in
`read_me/odeka_website_guide.tex` / `.pdf` — that's written for a human RA. This
file is written for a future Claude Code session. Read both.

If you (Claude) make a nontrivial discovery, add it here. Keep entries terse and
concrete — file paths, exact strings, exact commands — not narrative.

## What this is

Static site for ODEKA A.S.B.L. (a Kinshasa-based field research organization),
built with **Quarto** (`.qmd` → HTML). Source lives at repo root in numbered
folders (`00_index/`, `01_about/`, `02_people/`, `03_projects/`, `04_news/`,
`05_jobs/`, `06_contacts/`, `07_legal_notice/`); built output goes to `docs/`
(that's the GitHub Pages publish source — **never hand-edit anything under
`docs/`**, it's fully regenerated by `quarto render`).

Deploy = `git push origin main` after a full `quarto render`. GitHub Pages serves
straight from `docs/` on `main`. Remote is `git@github-odeka:odeka-asbl/odeka-asbl.github.io.git`
(note the custom SSH host alias `github-odeka`, not `github.com` — this machine
has an SSH config entry for it).

## The #1 recurring bug: case-sensitive image paths

**This has bitten this exact repo twice now.** macOS's filesystem is
case-insensitive, so `image.JPG` and `image.jpg` are the *same file* locally —
everything looks fine in `quarto preview` and in `git status`. GitHub Pages runs
on case-sensitive Linux, so if the file committed in `docs/` has different case
than what the generated HTML's `<img src>` requests, it 404s **only in
production**, invisibly, with zero local warning signal.

- Incident 1 (earlier session): `news20220627.qmd` referenced `news20220627.JPG`
  while the actual source file was `news20220627.jpg`. Fixed by editing the
  `.qmd` to match.
- Incident 2 (2026-08-16): the *source* was already fixed, but the **built
  `docs/04_news/images/news20220627.JPG`** was still tracked in git with the old
  uppercase name from before that fix — a stale build artifact `git status`
  never flagged as dirty (again, case-insensitive FS hides the diff). The user
  reported it as "image not visible on Safari" after pushing. Root cause found
  via `git ls-tree HEAD` (shows what's *actually* committed, case and all) vs
  `grep` of the built HTML's `<img src>` values.

**If a user reports a missing image on the live site (but it looks fine
locally):** don't start with browser debugging — start here:
```bash
# What's actually committed, case-sensitive:
git ls-tree -r HEAD --name-only docs/ | grep -E '\.(JPG|JPEG|PNG|GIF)$'
# For each hit, check what case the generated HTML actually references:
grep -n "<exact-lowercase-name>" docs/path/to/page.html
```
If a tracked `docs/` filename's case doesn't match what the HTML requests, fix
it with a two-step rename (a single `git mv` between two names that only differ
by case is a no-op on this filesystem):
```bash
git mv docs/path/FILE.JPG docs/path/FILE_tmp.jpg
git mv docs/path/FILE_tmp.jpg docs/path/FILE.jpg
```
Then `quarto render` again and re-check `git status` is clean before committing.
Consider running the full `git ls-tree` sweep above proactively any time you touch
image files or do a cleanup pass — don't wait for a bug report.

## Design system

- **Serif body font**: Cambria throughout (`"Cambria Math", Cambria, serif` in
  several rules) — this is the site's identity; don't let new content fall back
  to Bootstrap's default sans-serif. This has happened by accident multiple
  times (People page entries, News/Jobs listing summaries) because Quarto's
  defaults are sans-serif and only *some* elements had serif rules applied.
- **Two reds, intentionally different, don't conflate them**:
  - `rgb(178, 49, 40)` — the muted brand red. Titles, links, person names,
    accents. This is the "correct" current red.
  - `rgb(196, 18, 18)` — a separate, more vivid red used for decorative bars/
    dividers/quote-marks elsewhere (e.g. `.home-projects-rule`,
    `.about-quote-band` quote bar). This is NOT a legacy color to "fix" — it's
    deliberately a different, brighter red for decorative elements vs. text.
  - History: `h1.title` titles used to be `rgb(196, 18, 18)` (vivid) and were
    changed to `rgb(178, 49, 40)` (muted) for consistency with body text. If a
    title looks like the wrong red, check the *specific* rule that paints it —
    see the CSS specificity trap below.
- Left-bracket title decoration (`title-bracket-wrap`, `/odeka_logo_left_bracket.png`)
  appears on every page that has a title (About, People, Projects, News, Jobs).
  Home, Contacts, and Legal Notice have no title element and don't get it.
- Diamond glyph (`◆`) is the site's recurring "mark" — section dividers, TOC
  active-item indicator, image/title seam markers. When adding a new divider or
  section break, match this motif rather than inventing a new one.

## CSS specificity traps encountered in this codebase

1. **A more specific *nested* rule can silently override an outer one you just
   edited.** `h1.title` and `main.content:has(.full-width-banner) h1.title
   .title-text` are both real, separate rules in `styles.css` — the second is
   more specific and is the one actually painting visible title text on pages
   with the banner. Editing only the outer rule and checking with
   `getComputedStyle` on the outer element can *look* correct while the
   rendered pixel is still wrong. **When a user disputes what color/style
   something is rendering, verify by sampling actual pixels (screenshot +
   pixel-read), not just `getComputedStyle` on the element you assume is
   painting it.** This produced a real, embarrassing wrong-answer incident
   earlier in the site's development.
2. There's a second, independent copy of several of these rules scoped to
   `.quarto-about-jolla:has(...)` — the About page uses Quarto's `jolla`
   template, which needs the *same* styling maintained in a second selector.
   Any time you fix something in the general `main.content:has(.full-width-banner)`
   rules, check whether an About-page/jolla equivalent needs the same fix.
3. **Bootstrap/Quarto ship ID-scoped rules** (e.g.
   `#title-block-header.quarto-title-block.default .quarto-title-meta`,
   `.breadcrumb`, TOC `:hover`/`.active` link colors) that plain class
   overrides — even multiply-qualified ones — cannot out-specify. Use
   `!important` in these specific, confirmed cases; don't reach for it by
   default elsewhere.
4. `overflow:hidden` as a clearfix will clip negative-margin children (bit us
   on person-photo/name cap-height alignment). Use a `::after { clear: both }`
   pseudo-element clearfix instead — see `.person-info::after` in `styles.css`.
5. Pandoc wraps bare markdown text lines in `<p>` tags automatically. A
   same-specificity sibling/descendant rule targeting `p` can silently beat a
   parent `div`'s intended color via normal cascade (not actually a
   specificity bug, just an easy trap) — fix with a more specific compound
   selector, e.g. `.person-info .person-name p`.
6. `:has()` is used extensively for page-type-conditional styling (e.g.
   `main.content:has(.job-page) .description`) because Quarto doesn't add
   per-page-type body classes by default. This is the established pattern —
   follow it for new page-type-specific CSS rather than inventing a different
   mechanism.

## The People page TOC sidebar (`nav-brackets-include.html`)

Included site-wide via `_quarto.yml`'s `include-after-body: nav-brackets-include.html`.
Contains `correctSidebarOverlap()`, which stops the floating `#quarto-margin-sidebar`
TOC from overlapping the closing banner at the bottom of the People page and
freezes it in place instead of letting it scroll under/behind content.

Non-obvious design decisions baked into that script, in case it ever needs
touching again:
- The "stuck" position is measured **once, on page load** — not live, sampled
  during the scroll event. Live sampling during fast/jump scrolling (End key,
  scrollbar drag) caught the sidebar mid-transition and produced wrong,
  jumpy values. Static measurement on load is deliberate, not a simplification
  that got left in.
- The freeze uses `position: fixed` with an **explicit `left`** captured at
  measurement time, not just `top` — without it, the sidebar collapses to the
  viewport's top-left corner when frozen (grid layout context is lost).
- CSS transitions (`transition: top ...`) must be explicitly suppressed
  (`transition: none !important`) around the freeze/unfreeze switch, with a
  forced reflow (`void el.offsetHeight`) in between, or the browser's
  transition easing produces a visible drift artifact during the switch
  (classic FLIP-pattern gotcha).
- The fade-out as the sidebar approaches the freeze point is a **continuous,
  scroll-linked opacity calculation**, not a binary show/hide — a discrete
  toggle produced a visible "it drops into place, then fades" artifact. Current
  tuned constants: fade starts 450px before the freeze scroll position, ends
  20px after.

## The News on/off switch

Three files change together, all tagged with a `NEWS SWITCH` comment:
1. `_quarto.yml` — commented-out `render: ["*", "!04_news/**"]` (the glob **must**
   be `!04_news/**`, not `!04_news/` — the latter silently excludes nothing) +
   the News navbar entry.
2. `index.qmd` — the `news_carousel` listing's YAML **definition** must also be
   commented out when off, not just its placement. An unplaced-but-defined
   Quarto listing gets **auto-appended at the very end of the rendered page**
   instead of being suppressed — found this the hard way.
3. `index.qmd`'s `{{< include 00_index/news_section_on.qmd >}}` line — swap the
   filename to `00_index/news_section_off.qmd` (a plain divider, no heading/
   carousel) to turn it off. This uses Quarto's `{{< include >}}` shortcode
   (literal text substitution at build time), specifically **not** an HTML
   comment toggle.

**Why not HTML comments for the on/off content?** Tried it first. Quarto's
listing-placement pre-scan (looking for `:::{#id}` markers) runs independently
of Pandoc's normal HTML-comment suppression, so both the "on" and "off" content
leaked through simultaneously in testing regardless of `<!-- -->` wrapping. The
`{{< include >}}` file-swap guarantees exactly one valid content block exists at
build time — no partial-parsing ambiguity. Don't revisit the comment approach.

Confirmed empirically (twice) that a full `quarto render` automatically prunes
already-built `docs/04_news/` output when News is excluded — no manual deletion
of `docs/04_news/` needed.

Current state as of the last push: **News is ON**.

## Quarto/build gotchas

- **Root-level `.md` files get rendered as live pages unless excluded** — Quarto
  has a built-in exception for `README.md` (never rendered) but nothing else is
  special-cased. When `CLAUDE.md` was first added at the repo root, the very
  next `quarto render` silently published it as `docs/CLAUDE.html` and added it
  to `docs/sitemap.xml` — internal notes, live on the public site. Fixed by
  adding an explicit `render:` list in `_quarto.yml`'s `project:` block
  (`"*"` then `"!CLAUDE.md"`), which the News on/off switch below now shares.
  **If you ever add another root-level `.md` file that isn't meant to be a
  page, exclude it there too, and check `git status` after rendering for a
  surprise `docs/<name>.html`.**
- **A stray background `quarto preview` process** (seemingly auto-started by VS
  Code's Quarto extension) has intermittently overwritten fresh `quarto render`
  output with stale content during this project's development, causing
  confusing flip-flopping results while testing changes. If a render doesn't
  seem to "take," check for and kill lingering preview processes before
  concluding something else is wrong:
  ```bash
  pkill -f "quarto preview"
  ```
- Quarto `listing:` definitions use `include:`/`exclude:` field filters (e.g.
  Projects uses `type: major` / `type: other` and `status: ongoing` / not, to
  drive which carousel a project appears in). If a new project doesn't show up
  where expected, check its frontmatter `type`/`status` values against what the
  listing on `03_projects/index.qmd` actually filters for — this is a common
  silent-omission trap, not a rendering bug.
- `about: template:` matters a lot visually: `marquee` = large full-width
  banner (News, Jobs, and now all Projects posts). `solana` = small sidebar
  photo (previously used for Projects posts — user disliked it, all three
  posts were switched to `marquee` to match News's layout). `jolla` = About
  page's specific profile-style template (needs its CSS rules mirrored
  separately, see specificity trap #2 above). `trestles` = Contacts/Legal
  Notice.
- Job/News/Project post pages hide Quarto's auto-generated duplicate
  description text under the title via a per-page `<style>` block (`display:
  none !important` on `header.quarto-title-block .description` etc.) — this is
  boilerplate copy-pasted at the top of every post `.qmd`, not a global CSS
  rule, because it's specific to pages using `about: template:` with a
  `description:` frontmatter field.
- `language:` frontmatter key overrides Quarto's built-in UI strings — used on
  Jobs posts to relabel "Author" → "Supervisor"/"Supervisors"
  (`title-block-author-single`, `title-block-author-plural`,
  `listing-page-field-author`) since the people listed there are supervisors,
  not literal authors of the posting text (which is verbatim J-PAL copy).

## Content conventions worth knowing

- **Jobs postings are verbatim.** Per explicit user instruction: job posting
  body text is copy-pasted exactly from the original J-PAL posting (ODEKA is
  the actual employer; J-PAL is just the advertising platform) — "the layout we
  adapt, the wording we keep." Don't paraphrase/rewrite job posting body text
  even if it reads awkwardly; only the surrounding page chrome (meta block,
  breadcrumb, section styling) follows house style.
- **News post authorship** currently reads `- The Research Associate Team` on
  all existing posts (deliberately, per explicit user correction — an earlier
  attempt to attribute them to "Adrien Foutelet" was reverted). If a real
  person wants credit for a specific post, that's an individual, opt-in
  decision — the *convention*, if adopted, would be to change that one post's
  `author:` field to the actual writer's name, not to change the default.
- Image/asset naming and location conventions are documented in
  `read_me/odeka_website_guide.tex` under "Where Images Live, and How They're
  Named" — follow that table strictly. This repo has already accumulated real
  cruft from not doing so (a `good pics/` folder of unused images, ~10 more
  confirmed-orphaned images cleaned up in one pass, the case-sensitivity bug
  above). When adding an image, name and place it per that convention the first
  time.
- Full names are missing for several People-page entries (Senior Management
  coordinators, several Senior Enumerators) and photos are missing for those
  plus current PhD Students — this is tracked as known-incomplete in the
  guide's "What Remains To Be Done" section, not a bug to silently fix by
  guessing.
